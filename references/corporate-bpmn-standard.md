# Внутренний корпоративный стандарт отрисовки BPMN

Источник: `docs/standards/Правила отрисовки схем в нотации BPMN.doc`
(экспорт Confluence, HTML/MIME; извлечён текстовый слой, без OCR).
Регламент описан для MS Visio, но правила применяются к любому инструменту,
включая draw.io.

Приоритет оформления (раздел 1 дельта-ТЗ):

```
внутренний корпоративный стандарт
>
правила BPMN Lite проекта (TZ_BPMN_GENERATOR_CLAUDE.md)
>
стандартные значения bpmn-diagrams
>
автоматический layout draw.io
```

Примеры-иллюстрации из исходника (~38 встроенных изображений в MIME) не
извлекались — текстовые формулировки ниже однозначны и покрывают все
проверяемые правила; изображения не добавляют новых фактов.

## Общие правила

- Схема читается слева направо, сверху вниз.
- Не ставить последовательные блоки друг над другом в разных дорожках, если
  действия не происходят одновременно.
- Переход к следующему блоку в другой дорожке — только из правого торца в
  левый торец блока.
- Если текст не помещается в блок задания — растянуть блок в ширину; высота
  всех блоков на схеме должна быть одинаковой.
- Блоки и другие элементы схемы — на одинаковом расстоянии друг от друга.
- Текст не должен накладываться на значок типа блока (при необходимости —
  перенос первой строки).
- Task имеет компактный размер 120–160 × 70–90 px; маркер типа — 14–16 px.
- В Task виден только короткий операционный `name` без HTML и без карточки
  render-контракта; целевой объём — 2–3 строки.
- Подпись наименования системы, артефактов, входов/выходов, условий шлюзов —
  размер шрифта **8**.

## Соединительные линии

- Блок ↔ блок: соединительная линия типа **«Поток управления»** (Sequence
  Flow).
- Блок ↔ документ/артефакт: соединительная линия типа **«Сопоставление»**
  (Association) — НЕ Sequence Flow.
- Прошлый процесс → начало нового: соединительная линия типа **«Поток
  обработки сообщения»** (Message Flow); прошлый процесс выносится НАД
  схемой, не остаётся внутри текущего пула.
- Каждая Association использует собственный порт и коридор. Разные связи не
  объединяют и не проводят по общему ненулевому сегменту.
- Порт обязан лежать на фактическом контуре: прямоугольнике Activity или
  Participant, ромбе Gateway, окружности Event либо безопасном поддерживаемом
  периметре Data Object. Каждый конец связи проверяется повторно по SVG.

## Вход в процесс (типы стартового события)

Поддерживаемые: неопределённый, сообщение, таймер, условие, сигнал,
множественный, параллельный многоэкземплярный.

Не используем: ошибка, эскалация, компенсация.

Если протокол не называет конкретный триггер — использовать
**неопределённый** Start Event, не угадывать тип.

Если входящий Message Flow от внешнего Participant запускает процесс,
использовать Message Start Event и экспортировать `messageEventDefinition`.

Если процесс может начаться по нескольким независимым причинам и порядок
действий не зависит от триггера — стартовое событие **«Множественный»**.
Если порядок действий отличается по триггеру — «Множественный» + **шлюз
«Исключающий шлюз событий»**, выбранное условие — как промежуточное событие
без заливки цветом.

## Условия и шлюзы

- **Эксклюзивный (XOR)** — альтернативные маршруты, выбирается один.
- **Неэксклюзивный/Включающий (OR)** — один или несколько маршрутов.
- **Параллельный (AND)** — все маршруты активируются одновременно.
- **Исключающий шлюз событий** — выбор первого события, которое случится.

Если две или более ветви потока реально соединяются — обязательно сделать
слияние (merge). Merge с fan-in меньше двух запрещён и не добавляется ради
симметрии со split. **Вопрос/условие пишется только на первом
(split) шлюзе.** Merge-шлюз — без вопроса и без пояснительного текста.

Если ветвей потока больше, чем выходов из параллельного шлюза — шлюз
дублируется.

Цикл реализуется через шлюзы: условие пишется только на **втором** шлюзе
(на входе в повтор), возвратная линия идёт по внешнему контуру.

## Артефакты процесса

Типы (визуально различны):

| Тип | Назначение |
|---|---|
| `print_form` | печатные формы/этикетки, печатаемые из системы блока |
| `system_document` | документ системы, указанной для блока |
| `external_document` | документ из внешней системы, рукописный |
| `system_report` | отчёт системы |

Правила:

- Артефакты **всегда рисуются под блоком**, никогда не в отдельной дорожке.
- Связь блок↔артефакт — только типом «Сопоставление» (Association).
- Семантические endpoints остаются `Artifact ↔ Activity`; технические порты
  являются только точками подключения на нижней границе Activity.
- Входы и выходы получают разные порты. Несколько Association одной Activity
  получают разные порты и коридоры и обходят role/system overlays, Activity и
  другие артефакты.

## Наименование дорожки

`"Номер подпроцесса" + "Наименование процесса" + "." + "Наименование
подпроцесса"` (применимо не ко всем проектам — используется, когда схема
единая для нескольких процессов/подпроцессов). Для одиночного процесса
(как `PURCHASE_RF`) — просто наименование дорожки = бизнес-роль, без
дополнительного префикса.

## Связь с проектным правилом ROLE ≠ SYSTEM

Этот документ описывает *как рисовать* линии/шрифты/артефакты/шлюзы.
*Что становится дорожкой* — отдельное, более строгое правило проекта:
см. [`system-role-policy.md`](./system-role-policy.md) — программная
система никогда не становится Lane/Pool, только подпись под Task.
